# Colony surface grid: surface objects and crater/building cells

Status: confirmed (static disassembly of the GOG flat,
`build/flat/FRAGILE.EXE.flat` + `build/named/FRAGILE.EXE.flat/decompiled.c`)
cross-checked against savegame dumps (`SAVEGAME.000`, `SAVEGAME.009`).
Source: disassembly + savegame dump; runtime trace still deferred.

## The colony "grid" is three layers

The colony surface (the view in which buildings are placed) is built from
three layers, per asteroid:

1. the **terrain surface grid** — the count×count (25..31 per side) grid
   generated by the `asteroid_regenerate` terrain chain from the asteroid's seed
   (see `docs/mechanics/asteroid-spawning.md`);
2. **surface objects** — 84-byte nodes (pool `g_surface_obj_pool` 0x168a8,
   1300 nodes) created from a static **terrain-record table**, one set per
   asteroid type;
3. **cells** — small nodes on each surface object's own sub-list that carry
   the actual **grid coordinates** (0..31 words) of craters and buildings.

## The terrain-record table

- Records: **0xAB69**, stride **0x14** (20 bytes), subtype byte at **+0x0A**.
- Per-type index ranges: BSS at **0x166F8** (start) / **0x16700** (end),
  stride **0xC** per asteroid type (entry = {start, ?, end}).
- The loop bounds at 0x166F8/0x16700 are runtime-filled BSS; no static writer
  was found (the new-game setup 0x228e4 is the suspected filler, unrecovered).
- **Anomaly note**: 0xAB69 lies in the code region of the flat (the bytes
  decode as instructions), the same "tables in code" problem documented for
  0x9c9c/0x9cd8/0x9cb0/0x9d78/0x9da0 in `asteroid-spawning.md`. The record
  values (subtype bytes) are therefore **unverified statically**; the access
  structure is verified.

## Surface-object creation at asteroid creation

`asteroid_assign_index` (0x22b94) creates the surface objects:

- **Wild path** (types 9..14, inline loop at 0x22e37..0x22e7d): for each
  record in the type's range whose subtype byte (0xAB69 + i·0x14) is **5**,
  one surface object via `FUN_00019804` (0x19804).
- **Faction path** (types 1..8): `FUN_00010f74` (0x10f74), called from
  0x22e88 when `[0x1660c]` (fixed-asteroid flag) != 0; per record:
  - subtype 7 → 1 object;
  - subtype **5 or 2 → 6 objects**;
  - subtypes 1/0/3/4/6 → **30 objects** each.
- **Multiplayer path**: `FUN_00010e84` (0x10e84), called from 0x22e9a when
  `g_mode_flag` != 0; subtype 5 or 2 → 1 object each.

### Surface-object node layout (`FUN_00019804`)

| offset | field |
|--------|-------|
| +0x08 | terrain-record index |
| +0x09 | owner type (copied from the asteroid's +0xc0) |
| +0x0A | flag (record-derived; from 0xab5c word) |
| +0x10 / +0x18 | behaviour pointers from the per-subtype table at 0xAFEC (8-byte entries, set by `FUN_0001d284`) |
| +0x14 | owning asteroid pointer |
| +0x30 | behaviour subtype (1 or 0xd, via `FUN_0001d284`) |
| +0x48.. | small index list into the 0xAA4C word table (count from 0xAB60) |
| +0x50 | word from 0xAB5E (record-derived) |
| +0x52 | byte from 0xAB5F (record-derived) |

The record-derived fields come from the 0xAB5x region (code-like bytes, same
anomaly — runtime values unverified).

## Cells: the actual grid coordinates

Each surface object carries a **NULL-terminated sub-list at +0x0C** whose
nodes are the colony cells:

| offset | field |
|--------|-------|
| +0x00 | next cell (NULL-terminated) |
| +0x04 | **subtype: 1 = building, 2 = crater** (3 = ship/missile) |
| +0x08 | owning asteroid pointer |
| +0x0C | asteroid seed (compared against [asteroid+0x88]) |
| +0x10..+0x1B | **6 grid-coordinate words** (0..31, the count×count grid) |

The 6 words are consumed by the colony-view sprite builder (roles
unconfirmed; see below).

## Colony-view sprite building

`FUN_0001bf14` (0x1bf14) runs over the player's surface objects (object +0x09
== `g_player_index`) and calls `FUN_000485f4` (0x485f4), which walks the
object's cell list and builds sprites:

- **Building cells (subtype 1)**: allocates a 365-byte sprite node via
  `FUN_00048394` (0x48394), fills it from the cell's 6 grid words, converts
  them to screen data via the scale table at **0x33258** (clamped to 0..31,
  result 0x3329F − value) and per-part table 0x395FC, and links the node into
  the asteroid's +0xB8 list. Node fields: +0x20 = sprite base (0x379A4),
  +0x24 = asteroid name pointer (+0x4C), +0x40 = 0x332A0, then 6 × 12-byte
  parts {0x395FC value, grid word, screen delta}.
- **Crater cells (subtype 2)**: a single shared 60-byte crater node
  (`[0x8701c]`, allocated via `FUN_00048394(2, 60)`) holds up to **8 craters**
  (count at **0x87020**, hard cap 8 at 0x486d3). Each crater entry: image base
  0x3B84, asteroid name pointer, position-derived values from the asteroid's
  +0x44/+0x48.
- **Ship/missile cells (subtype 3)**: 60-byte node via `FUN_00048394(2, 60)`
  plus `FUN_00036014` (0x36014).

Support state at **0x87014..0x87060** (the "asteroid view" scratch area):
owner table at **0x87024** (init at 0x48114: `g_player_index` first, then up
to 15 owners whose bit is set in the mask at **0x16614**), crater count at
0x87020, crater node pointer at 0x8701C. The crater/temp-building image lists
use list heads embedded in the message strings at 0x86e32/0x86f3b (+5 / +0xe).

## Verified from saves (home asteroid AST:GEA-989)

SAVEGAME.000/009 node dumps confirm the runtime struct on disk:

| offset | field | value |
|--------|-------|-------|
| +0x88 | asteroid seed | **0x50269FDC** |
| +0x8C | size parameter | 27 |
| +0x90 | grid bitmap pointer | 0x78F84 (sim-heap) |
| +0xC0 | type | 1 (TetraCorp home) |

The +0x88 seed **corrects** the simulated value 0xa16c7d02 in
`asteroid-spawning.md` (the save is ground truth; the RNG simulation was
wrong).

**No asteroid has surface objects in any save**: every asteroid's +0x0C
anchor is self-referential/empty, and the building pool is entirely free. In
the GOG campaign the per-type record bounds (0x166F8) are therefore never
filled on the start path — the colony grid is created **lazily at runtime**.

## The lazy creator: "Create_Surface_Map" (unrecovered)

The sim-level function whose debug string is `Create_Surface_Map - memory
fail` (0x86298) is the lazy creator. It sits in **unrecovered gap code**; the
string has no recoverable xrefs (no imm32/pointer dword in the flat). Its
caller chain and the exact cell-creation loop (how the 6 grid words are
assigned — plausibly Sky-Hook-centred placement, per the in-game text
"The building will be constructed close to where the Sky Hook is") need a
DOSBox-X trace or gap-function disassembly.

## Open questions

- Where/when `Create_Surface_Map` is called (colony-view entry? colonisation?)
  and how the cells' 6 grid words are computed — needs a trace.
- Runtime values of the record table 0xAB5x and the bounds 0x166F8/0x16700
  (code-like bytes in the flat; same anomaly as the other "tables in code").
- The role of the 6 words per building cell (construction stages? sub-sprite
  positions?) and the 0x33258 scale table values.
- The per-type record ranges: what fills 0x166F8 (suspected: the new-game
  setup 0x228e4; unrecovered).
- The savegame `BUILDING` section is the 8000 × 24-byte building pool dump
  (all free in observed saves) — building node internals still undecoded.
